XXE & Cookie Forgery on Play Framework

A full academic and practical walkthrough of a web attack chain exploiting XML External Entity injection and session cookie forgery.

Read Tutorial

Overview

This write-up documents a practical hacking tutorial developed in an academic context for the Master's degree in Information Security Engineering. The attack targets a vulnerable web application built using Play Framework version 2.1.3 and demonstrates a complete exploitation chain combining XXE injection and session cookie forgery.

Academic Context

This work was developed as part of the course Penetration Testing and Exploit Development at the Polytechnic Institute of Beja. The objective was to simulate a real-world web attack in a controlled and authorized environment.

Target Environment

  • Web Framework: Play Framework 2.1.3
  • Architecture: Model-View-Controller (MVC)
  • Server OS: Linux (VirtualBox VM)
  • Attacker OS: Kali Linux
  • Primary Vulnerability: XXE (CVE-2014-3630)

Vulnerability Analysis

The Play Framework version used in this scenario relies on Java-based XML parsers that, by default, do not fully disable external entity resolution. This misconfiguration enables XML External Entity (XXE) attacks, specifically of the Out-of-Band (OOB) type.

Although the web application primarily communicates using JSON, the backend endpoint continues to accept and process XML requests, exposing the vulnerable XML parser.

Figure 3.1: Original request between the web page and the server

Figure 3.2: Server response to an XML request

Additionally, Play Framework uses stateless sessions stored entirely on the client side in signed cookies. If the application secret key is compromised, session forgery becomes possible.

XXE Technical Background (CVE-2014-3630)

The vulnerability exploited in this scenario is identified as CVE-2014-3630, affecting Play Framework versions prior to secure XML parser hardening.

The root cause lies in the default Java XML parser configuration used by Play Framework 2.1.3, which does not explicitly disable the resolution of external entities or external DTDs.

While the application attempts to mitigate in-band XXE attacks (where extracted data is reflected directly in the HTTP response), it remains vulnerable to out-of-band (OOB) XXE attacks.

In OOB XXE, sensitive data is exfiltrated via secondary network requests initiated by the XML parser itself, effectively bypassing application-level output controls and firewall restrictions.

Attack Phases

1. Reconnaissance

The first phase of the attack focused on reconnaissance and service discovery. The goal was to identify exposed network services, application technologies, and potential entry points for exploitation.

An initial TCP scan was performed using Nmap with default scripts and version detection enabled: 

nmap -sC -sV 192.168.1.177 -oN nmap.txt

The scan revealed multiple open services, most notably:

  • SSH service running on port 22
  • HTTP web application on port 80
  • MySQL database service on port 3306

Figure 4.1: Nmap scan results identifying exposed services

Since a web service was available, directory enumeration was performed to identify hidden endpoints and application functionality. 

dirb http://192.168.1.177/

Figure 4.2: Directory enumeration revealing application paths

The enumeration results pointed to a login interface, indicating the presence of authentication logic and session handling mechanisms.

Figure 4.3: Web application login page

2. XXE Exploitation (Out-of-Band)

During request interception with Burp Suite, it was observed that the backend endpoint accepted XML payloads in addition to JSON. This behavior is particularly dangerous when XML parsers are not securely configured.

The original request was modified by changing the Content-Type header to text/xml, allowing a crafted XML payload to be processed by the server.

Initial attempts at in-band XXE failed due to server-side output restrictions. However, the application remained vulnerable to Out-of-Band (OOB) XXE, which allows data exfiltration through external network requests.

Figure 4.4: Out-of-Band XXE request reaching the attacker server

An external DTD was hosted on the attacker machine using Python’s built-in HTTP server: 

python3 -m http.server 80

The malicious DTD defined an external entity pointing to sensitive files on the target system:

%eval;

The intercepted XML request was then modified to reference the external DTD:

As a result, the contents of /etc/passwd were successfully exfiltrated to the attacker’s HTTP server.

Figure 4.7: /etc/passwd exfiltrated via XXE

Analysis of the extracted /etc/passwd file revealed a user named play, whose home directory pointed to /opt/play-2.1.3/. This strongly suggested the application installation path.

Using the same out-of-band XXE technique, directory listings were enumerated by targeting internal paths such as: 

file:///opt/play-2.1.3/

This revealed standard Play Framework directories, including conf/, which ultimately contained the application.conf file holding the application secret.

3. Session Cookie Forgery

Play Framework implements stateless, client-side sessions. This design choice means that all session data is stored entirely inside a browser cookie rather than on the server.

To ensure integrity, the cookie is cryptographically signed using an application-wide secret key defined in application.conf. However, the session contents are not encrypted, only signed.

If the secret key is compromised, the server can no longer distinguish between legitimate session cookies and attacker-generated ones, resulting in a complete authentication bypass.

Using the previously demonstrated XXE out-of-band technique, the file application.conf was successfully retrieved from the server filesystem.

Figure 4.8: application.conf revealing the Play Framework secret key

To understand how session cookies are generated and validated, the Play Framework 2.1.x source code was reviewed directly. The analysis focused on the Session class and the internal signing mechanism.

Source code reviewed at:
https://github.com/playframework/playframework/tree/2.1.x

Figure 4.9: Play Framework Session class source code

The Session class is responsible for serializing session data into key-value pairs and encoding them into a single string that is stored as a browser cookie.

Figure 4.10: sign() function used by Play Framework

The sign() function applies an HMAC-SHA1 operation to the serialized session data using the application secret key. The resulting signature is appended to the session value.

During each request, the server recomputes the signature and verifies its integrity. No server-side session state or additional validation is performed.

  • Session data serialized as plaintext key-value pairs
  • Integrity enforced using HMAC-SHA1
  • Signing key stored in application.conf
  • No server-side session storage or validation

Based on this analysis, the signing algorithm was reimplemented in Python to generate arbitrary session cookies that would be accepted as valid by the server.

Figure 4.13: Cookie signing logic recreated in Python

A forged session containing administrative privileges was generated and manually injected into the browser using the developer tools.

Figure 4.14: Forged session cookie inserted into browser

Figure 4.15: Administrative access successfully obtained

This confirms that once the Play Framework secret key is exposed, the entire authentication mechanism can be bypassed without exploiting additional server-side vulnerabilities.

4. Post-Exploitation

After gaining administrative access to the application, the final phase focused on achieving system-level access.

Previously discovered usernames were tested against the SSH service using Metasploit’s SSH login module.

Figure 4.16: SSH login modules in Metasploit


use auxiliary/scanner/ssh/ssh_login
set RHOSTS 192.168.1.177
set USER_FILE users.txt
set PASS_FILE passwords.txt
run

Figure 4.18: Successful SSH authentication

Once logged in, privilege escalation was achieved using misconfigured sudo permissions.

Figure 4.20: Root privileges obtained

Although the root account did not have a valid password hash in /etc/shadow, the compromised user was configured as a sudoer.

This allowed privilege escalation via: 

sudo su

Misconfigured sudo privileges are a common post-exploitation issue and frequently lead to full system compromise.

Defensive Measures & Mitigation

From a defensive perspective, this attack chain could have been prevented through a combination of secure configuration, defensive coding practices, and system hardening.

  • Disable XML external entity resolution explicitly
  • Reject XML payloads when JSON is expected
  • Avoid client-side session storage for authentication
  • Protect and rotate application secret keys
  • Apply least-privilege principles to system users
  • Keep frameworks and dependencies up to date

Conclusion

This tutorial demonstrates how outdated frameworks and insecure default configurations can lead to complete system compromise. The attack chain highlights the importance of disabling XML external entities, protecting cryptographic secrets, and avoiding client-side session storage.
